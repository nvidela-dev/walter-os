# Language & naming convention

This project follows a strict three-layer language split. Read this before adding
code or copy.

## The rule

| Layer | Language | Where |
|-------|----------|-------|
| **Code** — variables, types, functions, props, route folders, filenames | **English** | everywhere under `src/` |
| **UI copy** — every string the user reads | **Spanish** | only in `src/i18n/` |
| **Database** — physical table & column names | **Spanish** (unchanged) | the string args to Drizzle's `pgTable("…")` / `text("…")` |

There must be **no Spanish identifiers in code** and **no hardcoded Spanish strings
in components**. The only Spanish allowed outside `src/i18n/` is the physical DB
identifier strings in `src/db/schema/`.

## Why the DB stays Spanish

Drizzle decouples the JavaScript property from the physical column:

```ts
export const providers = pgTable("proveedores", {   // ← physical table (Spanish, frozen)
  name: text("nombre").notNull(),                    // ← JS prop English, column string Spanish
  debt: numeric("deuda", { precision: 10, scale: 2 }),
});
```

Code reads `provider.name` / `provider.debt`; the generated SQL still targets
`proveedores.nombre` / `proveedores.deuda`. This means **renaming code to English
required zero database migration** — the physical schema is untouched. The Drizzle
schema files remain the source of truth for the English-to-Spanish mapping.

## The i18n files

- **`src/i18n/messages.ts`** — all UI copy, nested by feature. Interpolated text is
  a function (`debtLabel: (amount) => …`).
- **`src/i18n/index.ts`** — re-exports `t`.

## Usage

```tsx
import { t } from "@/i18n";

<h1>{t.providers.title}</h1>                   {/* Proveedores */}
<button>+ {t.common.add}</button>               {/* + Agregar */}
<h3>{provider.name}</h3>                        {/* English prop, real data */}
<p>{t.providers.debtLabel(provider.debt)}</p>   {/* Deuda: $… */}
```

## Adding a feature

1. Add a feature namespace to `messages.ts` for its copy.
2. Define the physical database mapping in the relevant Drizzle schema file.
3. Write components with English identifiers, pulling all user-facing text from `t`.

## Why not next-intl / i18next?

The app is single-language (Spanish UI). A full i18n runtime adds a provider, async
loading, and key indirection we don't need. Typed `as const` dictionaries give
autocomplete, compile-time safety, and grep-ability today — and become the `es`
catalog for a real i18n library later with no rewrite.
